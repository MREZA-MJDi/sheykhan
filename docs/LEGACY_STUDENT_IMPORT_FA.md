# راهنمای ورود ۵۵ دانش‌آموز قدیمی WordPress به شیخان

## هدف و مرز داده

فایل منبع، خروجی کاربران WordPress/Tutor LMS است و شامل ۵۵ هویت یکتای تأییدشده می‌شود. این داده به‌تنهایی اطلاعات خرید دوره، پرداخت، پایهٔ فعلی، کلاس/گروه، مدرس، برنامه هفتگی، نمره یا سابقهٔ حضور و غیاب را تعیین نمی‌کند.

Import فقط این موارد را ایجاد یا همساز می‌کند:
- ردیف User با شناسهٔ میراث legacy_source=wordpress و legacy_id؛
- نقش عمومی student؛
- پروفایل پایهٔ Student برای حسابی که هنوز پروفایل ندارد؛
- عضویت فعال student در یک Academy فعال که مدیر صریحاً با academy-id انتخاب می‌کند.

این کار به‌معنی خرید/ثبت‌نام در Course، تأیید پرداخت یا عضویت در Classroom نیست و نباید به‌تنهایی دسترسی به محتوای دوره یا لینک کلاس ایجاد کند.

## چرا SQL اصلی را مستقیم اجرا نمی‌کنیم؟

فایل SQL اصلی علاوه بر ۵۵ INSERT، چند دستور گستردهٔ DELETE و UPDATE دارد که کاربران WordPress خارج از فهرست را از نقش/پروفایل دانش‌آموز خارج می‌کند و وضعیت آن‌ها را blocked می‌گذارد. اجرای کامل آن روی دیتابیس فعلی ممکن است حساب‌های دیگر یا سابقهٔ موجود را دست‌کاری کند.

در عوض، دستور Laravel منبع را فقط برای استخراج ۵۵ ردیف INSERT کاربر می‌خواند؛ بقیهٔ دستورهای SQL از جمله DELETE، UPDATE، START TRANSACTION و COMMIT از طرف Importer اجرا نمی‌شوند. منبع خام نباید در GitHub عمومی ذخیره شود.

## ۱. استقرار کد

پس از Merge/Deploy شاخه‌ای که این دستور را دارد، در ریشهٔ پروژه بررسی کن:

~~~bash
php artisan list | grep sheykhan:import-legacy-students
php artisan migrate:status
~~~

اگر دستور نمایش داده نشد، نسخهٔ Deployشده شامل فایل Importer یا ثبت Commandها نیست. اگر Migrationهای legacy_source و legacy_id یا فیلدهای لازم StudentProfile اجرا نشده‌اند، پیش از Import آن‌ها را در محیط مناسب اعمال کن.

## ۲. نگهداری خصوصی SQL

فایل را با SFTP یا روش امن دیگری روی سرور قرار بده، خارج از مسیر public/ و خارج از Git. برای نمونه:

~~~bash
install -d -m 700 storage/app/private
# فایل را به storage/app/private/legacy-students.sql منتقل کن
chmod 600 storage/app/private/legacy-students.sql
~~~

فایل شامل اطلاعات شخصی و هش رمزهای قدیمی است؛ در Pull Request یا مخزن عمومی Commit نشود. بعد از Import موفق و گرفتن تأیید، طبق سیاست نگهداری دادهٔ سازمانی آن را از سرور حذف/آرشیو امن کن.

## ۳. اول Dry-run

دستور بدون --apply فقط منبع و اسکیما را اعتبارسنجی می‌کند و دیتابیس را تغییر نمی‌دهد:

اول شناسهٔ یک Academy فعال و مورد تأیید را از محیط خودت پیدا کن؛ Importer عمداً Academy نمی‌سازد و از روی نام دانش‌آموز هم حدس نمی‌زند. بعد Dry-run را با همان شناسه اجرا کن:

~~~bash
ACADEMY_ID=123 # عدد 123 را با ID واقعی Academy فعال جایگزین کن
php artisan sheykhan:import-legacy-students storage/app/private/legacy-students.sql --academy-id="$ACADEMY_ID"
~~~

خروجی باید تعداد ۵۵ شناسهٔ یکتا را تأیید کند. اگر تعداد، ساختار ستون‌ها، نوع هش یا هویت‌ها با انتظار مطابق نباشد، Import باید متوقف شود. اگر خطای تعارض ایمیل دیدی، آن حساب را دستی تطبیق بده؛ Import نباید یک حساب فعلی را صرفاً به‌دلیل ایمیل مشترک تصاحب کند.

## ۴. گرفتن نسخهٔ پشتیبان و اجرای صریح

پیش از اعمال روی Production، از دیتابیس بکاپ قابل‌بازیابی بگیر و Dry-run را مرور کن. سپس:

~~~bash
ACADEMY_ID=123 # همان ID تأییدشده در Dry-run
php artisan sheykhan:import-legacy-students storage/app/private/legacy-students.sql --academy-id="$ACADEMY_ID" --apply
~~~

عملیات در تراکنش اجرا می‌شود، تکرار مجاز است و حساب‌های خارج از فهرست را مسدود یا حذف نمی‌کند. حساب legacy موجود با همان legacy_id دوباره ساخته نمی‌شود و password/status اصلاح‌شدهٔ حساب موجود بی‌دلیل بازنویسی نمی‌شود. در صورت برخورد یک ایمیل منبع با حسابی با هویت متفاوت، دستور متوقف می‌شود تا بررسی دستی انجام شود.

## ۵. وضعیت رمزهای WordPress

منبع شامل دو شکل از هش است:
- هش‌های WordPress با پیشوند $wp$2y$؛ این پیشوند فقط wrapper تزئینی نیست. احراز هویت باید فرایند pre-hash سازگار با WordPress را انجام بدهد. Importer هش اصلی را دقیقاً نگه می‌دارد و پس از احراز هویت موفق، آن را به هش فعلی Laravel تبدیل می‌کند.
- یک هش قدیمی phpass با پیشوند $P$؛ سرویس LegacyWordPressPassword آن را بررسی می‌کند و پس از ورود موفق، رمز به هش استاندارد Laravel تبدیل می‌شود.

این سازوکار نه رمز خام را استخراج می‌کند و نه رمز پیش‌فرض جدید می‌سازد. کاربر همچنان باید رمز اصلی خود را بداند، یا از جریان بازیابی/تکمیل هویت پشتیبانی‌شده استفاده کند.

## ۶. محدودیت هویت ورود - مهم

در فایل منبع:
- فقط ۲ رکورد از ۵۵ رکورد ایمیل دارند؛ ۵۳ رکورد email برابر NULL است.
- هیچ‌یک از ۵۵ رکورد شمارهٔ موبایل ندارد.

مسیر فعلی ورود به ایمیل تکیه دارد؛ بنابراین حساب فاقد ایمیل با اطلاعات فعلی الزاماً نمی‌تواند از فرم ورود استاندارد استفاده کند، حتی اگر ردیف User و hash رمز وارد شده باشد. برای این حساب‌ها باید قبل از استفادهٔ واقعی:
1. هویت دانش‌آموز را با فرآیند معتبر آموزشگاه تأیید کنی؛
2. ایمیل واقعی و یکتا یا شناسهٔ ورود اختصاصی و تست‌شده ثبت شود؛
3. در صورت استفاده از شناسهٔ ورود غیرایمیلی، خود LoginRequest/AuthController باید آن نوع شناسه را به‌صورت امن پشتیبانی کند؛
4. بازیابی رمز و محدودیت نرخ درخواست نیز برای آن شناسه بررسی شود.

به‌هیچ‌وجه برای رفع سریع مشکل آدرس ایمیل ساختگی نساز؛ این کار می‌تواند مالکیت حساب، بازیابی رمز و حریم خصوصی را خراب کند.

## ۷. پس از ورود دانش‌آموزان به User/StudentProfile

عضویت فعال در Academy در Importer با academy-id انجام می‌شود؛ اما این مراحل هنوز باید جداگانه با رکوردهای واقعی آموزشگاه انجام شوند:
1. انتخاب Course واقعی که دانش‌آموز در آن ثبت‌نام کرده؛
3. ثبت پرداخت/وضعیت پرداخت طبق شواهد معتبر؛
4. انتخاب Classroom مرتبط با همان Course؛
5. ثبت‌نام دانش‌آموز در CourseEnrollment و عضویت فعال در classroom_student از گردش‌کار پنل، به‌صورت همساز؛
6. تعریف برنامه هفتگی برای Classroom با یک ClassSchedule برای هر روز/بازه؛
7. تست فهرست دوره‌ها و کلاس‌های آنلاین با همان حساب دانش‌آموز.

گزینهٔ --block-unlisted به‌صورت پیش‌فرض فعال نیست. فقط در صورت تصمیم جداگانه و پس از فهرست‌برداری از حساب‌های موجود، می‌توان آن را اجرا کرد؛ این گزینه نقش student را از کاربران WordPress خارج از فهرست برمی‌دارد، عضویت student آن‌ها را آرشیو و حساب را blocked می‌کند. این رفتار destructive است و جایگزین SQL اصلی یا پاک‌سازی پیش‌فرض نیست.

فایل SQL منبع هیچ ارتباطی میان این ۵۵ دانش‌آموز و دوره یا مدرس خاصی تعریف نمی‌کند؛ این ارتباط را از روی نام یا حدس نساز.

## ۸. تست و بازبینی

پس از Merge، تست‌های مربوط را اجرا کن:

~~~bash
php artisan test --filter=LegacyStudentImportTest
php artisan test --filter=LegacyWordPressPasswordTest
php artisan test --filter=TeacherWorkspaceFlowTest
~~~

سپس در محیط آزمایشی این خروجی‌ها را بازبینی کن:
- تعداد هویت‌های جدید و پروفایل‌های ایجادشده؛
- عدم تغییر وضعیت یک کاربر WordPress که خارج از فهرست ۵۵ نفر بوده؛
- عدم تکرار User/Profile/role link در اجرای دوم؛
- امکان ورود یک حساب ایمیل‌دار با رمز legacy؛
- تکمیل دستی هویت برای حساب‌های فاقد ایمیل/موبایل؛
- اینکه هیچ‌یک از دانش‌آموزان به Course یا Classroomی که واقعاً برایش ثبت نشده دسترسی نگرفته باشد.

## منطق‌های مرجع

- Command: app/Console/Commands/ImportLegacyStudents.php
- بررسی phpass: app/Services/LegacyWordPressPassword.php
- Auth provider سازگار با WordPress: app/Auth/LegacyAwareUserProvider.php
- User: app/Models/User.php
- Enrollment و payment gate: app/Models/CourseEnrollment.php
- ثبت‌نام گروه و همسازسازی membership: app/Services/OwnerEnrollmentService.php
- کلاس/گروه: app/Models/Classroom.php
- برنامه هفتگی: app/Models/ClassSchedule.php
