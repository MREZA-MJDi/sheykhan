# ممیزی مسیرهای پنل‌ها و Design System — شیخان

این سند نقشهٔ smoke testهای صفحات ورودی و قراردادهای رگرسیون موجود را ثبت می‌کند. «صفحه با GET باز شد» با «تمام رفتارهای CRUD و مجوزها سالم است» یکسان نیست؛ برای همین مسیرهای نمایشی و رفتارهای نوشتنی جداگانه تست می‌شوند.

## ۱. خطای ۵۰۰ صفحهٔ اعضا

صفحه از مسیر `owner.people.index` وارد `PeopleController@index` و سپس `OwnerWorkspaceService::people()` می‌شود. مسیر پایهٔ اعضا و سه فهرست مدرس، دانش‌آموز و والد از رابطهٔ کاربران آموزشگاه صفحه‌بندی‌شده می‌آیند. تاریخچهٔ ورود دانش‌آموز یک بخش کمکی است و به جدول‌های `student_onboardings` و `academic_grades` وابسته است.

دو مسیر ۵۰۰ در صفحهٔ اعضا جداگانه بررسی شدند:

1. **Schema ناقص تاریخچه:** اگر جدول `student_onboardings` موجود باشد اما جدول `academic_grades` روی سرور هنوز deploy نشده باشد، رابطهٔ `requestedGrade` نباید query شود. سرویس و view حالا بخش تاریخچه را فقط وقتی فعال می‌کنند که هر دو schema کامل باشند؛ بقیهٔ فهرست اعضا از این بخش اختیاری مستقل می‌ماند. تست رگرسیون همین وضعیت partial-migration را شبیه‌سازی می‌کند.
2. **قیمت تهی دوره:** CI یک خطای واقعی دیگر را بازتولید کرد؛ گزینهٔ انتخاب دوره در همین صفحه `PersianUi::money($course->price)` را برای دورهٔ پولی با `price = null` صدا می‌زد. این ورودی باعث `TypeError` می‌شد و پاسخ ۵۰۰ می‌داد. نمایش حالا برای چنین موردی «قیمت تعیین نشده» می‌گوید و تست مستقلی این وضعیت را پوشش می‌دهد.

پس مورد قیمت تهی، علت قطعی در یکی از مسیرهای ۵۰۰ این صفحه است و برای partial schema نیز مسیر شکست جداگانه محافظت شده است. با این حال، برای نسبت‌دادن قطعی رخداد قدیمی کارفرما به یکی از این دو مورد، stack trace همان رخداد لازم است؛ اگر ۵۰۰ بعد از deploy ادامه داشت، اولین exception و خطوط اطراف آن در `storage/logs/laravel.log` را بررسی کن. راهنمای مرحله‌ای در `docs/AUTH_SESSION_500_TRIAGE_FA.md` قرار دارد.

## ۳. تست‌های عمیق موجود

- احراز هویت و سشن: `AuthenticationSessionLifecycleTest` چرخه ورود نقش‌ها، چرخش شناسهٔ نشست و خروج را بررسی می‌کند.
- داشبورد دانش‌آموز و مدرس: `StudentDashboardBackendContractTest` و `StudentTeacherDashboardContractTest` دادهٔ متصل به backend، محتوای مجاز، شمارش‌ها و بعضی حالت‌های دسترسی را بررسی می‌کنند.
- مسیرهای کاری مدرس: `TeacherWorkspaceFlowTest` مسیرهای اصلی کلاس، دوره، تکلیف و آزمون و چند عملیات تغییردهنده را آزمایش می‌کند.
- اونر/ادمین: تست‌های `OwnerAccessIsolationTest`, `OwnerClassroomManagementTest`, `OwnerPeopleLifecycleTest`, `OwnerMeetingWorkflowTest`, `OwnerEnrollmentTest` و تست‌های گزارش/محتوا، عملیات و مرز دسترسی آموزشگاه‌ها را پوشش می‌دهند.
- والد و متخصص SEO: بخش والد در `StudentTeacherDashboardContractTest` و مسیرهای کلیدواژه در `SeoKeywordWorkspaceTest` دارای تست‌های feature اختصاصی هستند.
- پایداری کش: `OwnerCacheServiceTest` اطمینان می‌دهد خرابی cache اختیاری به‌تنهایی داشبورد را زمین نزند و خطای resolver پنهان نشود.

## ۴. Design System مشترک

`resources/css/panel-design-system.css` بعد از stylesheet اختصاصی هر نقش load می‌شود. هدف آن یکپارچه‌کردن پایه‌هاست، نه حذف تفاوت‌های کاری نقش‌ها:

- تایپوگرافی فارسی، رنگ متن/سطح، حاشیه و شعاع کارت‌ها؛
- ارتفاع کنترل‌های فرم، focus state، خوانایی پیام اعتبارسنجی؛
- رفتار جدول‌ها و overflow در صفحه‌های باریک؛
- bottom navigation، هدف لمسی و فاصلهٔ امن پایین صفحه؛
- رعایت `prefers-reduced-motion`.

معلم و دانش‌آموز از قاب، سطح‌ها و نوار ناوبری مشترک استفاده می‌کنند؛ والد و ادمین هم از پوسته و کارت‌های مشترک بهره می‌برند. اجزای خاص مانند فرم ساخت آزمون، گزارش مالی یا صفحهٔ اعضا همچنان به نیاز همان جریان کاری وفادار می‌مانند.

## ۵. معیار قبول قبل از merge / تحویل

1. سبز بودن build تولیدی Vite و تست‌های کامل SQLite و MariaDB روی آخرین commit همین PR؛
2. سبز بودن رگرسیون partial schema در صفحهٔ اعضا و تمام smoke testهای بالا؛
3. اجرای دستی در مرورگر روی دسکتاپ و موبایل برای منوهای باز/بسته، باتم‌بار، صفحه‌بندی، فرم‌های validation و خطای مجوز؛
4. اگر ۵۰۰ محیط کارفرما باقی ماند، دسته‌بندی stack trace واقعی به session/DB/cache/view/permission و اصلاح همان مسیر، نه پاک‌کردن کورکورانهٔ cache؛
5. عدم ادعای «بدون باگ» صرفاً بر اساس تست رندر؛ رفتارهای CRUD و مجوزها باید با feature tests و بررسی محیط تحویل تایید شوند.
