# راهنمای تشخیص خطای ۵۰۰ در ورود و پنل‌ها

این راهنما برای بررسی خطاهای موقتی ورود، انتقال به داشبورد، خروج و رندر پنل‌هاست. **کد ۵۰۰ به‌تنهایی ثابت نمی‌کند علت سشن است.** خطای DB، کش، Blade قدیمی، فایل‌های asset نامنطبق یا یک exception در صفحه نیز می‌تواند بعد از ورود دیده شود.

## ۱) اول خطای واقعی را ثبت کن

هنگام رخداد، ساعت دقیق و URL را یادداشت کن. سپس نزدیک همان ساعت را در فایل زیر ببین:

```text
storage/logs/laravel.log
```

از اولین خط exception و نام کلاس/فایل/خطی که بعد از آن آمده عکس یا متن بردار. در محیط production مقدار `APP_DEBUG` باید `false` باشد؛ جزئیات exception را در صفحه عمومی نمایش نده.

## ۲) بررسی‌های کوتاه روی سرور

از CMD یا ترمینال داخل پوشه پروژه اجرا کن:

```bash
php artisan about
php artisan migrate:status
php artisan route:list --path=login
php artisan route:list --path=logout
php artisan route:list --path=dashboard
```

مطمئن شو migration جدول `sessions` اجرا شده است؛ پیکربندی پیش‌فرض پروژه از `SESSION_DRIVER=database` استفاده می‌کند مگر اینکه در محیط نصب‌شده override شده باشد. مقدار مؤثر `SESSION_DRIVER`، `SESSION_TABLE`، `CACHE_STORE` و `APP_KEY` را با تنظیمات deploy مقایسه کن، اما secretها و مقدار APP_KEY را در پیام یا issue عمومی قرار نده.

اگر log به جدول `sessions` اشاره می‌کند، ابتدا migration و اتصال DB را رفع کن. اگر log به `cache` یا Redis اشاره می‌کند، مشکل cache store را بررسی کن. اگر خطا به Blade، route یا config cached مربوط است، ادامه بده.

## ۳) پاک‌سازی کنترل‌شده‌ی cacheهای Laravel

این دستورات برای بعد از ثبت stack trace یا پس از deploy کد جدید مفیدند؛ آن‌ها علت واقعی را مشخص نمی‌کنند:

```bash
php artisan optimize:clear
php artisan view:clear
```

بعد از آن build تولیدی assetها را بساز و deploy را با یک revision واحد کامل کن:

```bash
npm ci
npm run build
```

در صورت استفاده از config/route/view cache در فرایند deploy، آن‌ها را فقط پس از تنظیم صحیح environment و موفقیت build دوباره بساز. هرگز در هر درخواست، در هر restart یا به‌صورت زمان‌بندی‌شده `APP_KEY` را مجدداً تولید نکن؛ تغییر آن نشست‌های موجود را نامعتبر می‌کند.

## ۴) رفتار مورد انتظار ورود و خروج

- ورود موفق باید شناسه نشست را بازسازی کند.
- کاربر غیرفعال یا حذف‌شده نباید نشست معتبر بگیرد.
- مقصد کاربر باید بر اساس role باشد؛ آدرس `intended` نباید دانش‌آموز را به پنل اونر هدایت کند.
- خروج از مسیر POST انجام می‌شود، نشست را باطل می‌کند و توکن CSRF را دوباره می‌سازد.
- مجوز نداشتن باید پاسخ 403 بدهد، نه اینکه با دسترسی گسترده‌تر یا exception پنهان شود.
- شکستِ cache اختیاری نباید صفحه را زمین بزند؛ خطای واقعی دیتابیس نباید به‌عنوان «cache miss» پنهان یا چند بار تکرار شود.

## ۵) چه چیزی هنوز لازم است؟

برای تعیین ریشه‌ی خطای ۵۰۰ که در محیط واقعی گهگاه رخ می‌دهد، stack trace همان رخداد لازم است. تست‌های feature می‌توانند رفتارهای قابل تکرار را پوشش دهند، اما نمی‌توانند بدون log مشخص کنند سرور نصب‌شده از چه env، session store یا نسخه‌ی deploy استفاده کرده است. پس از ثبت خطا، exception را به یکی از مسیرهای auth/session، DB/cache، Blade/assets یا permission دسته‌بندی و همان مسیر را اصلاح کن.
