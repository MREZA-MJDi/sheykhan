# ممیزی نهایی UX، ساختار و آمادگی Production — شیخان

**تاریخ بررسی:** ۱۴۰۵/۰۸/۰۲ (۲۰۲۶-۱۰-۲۴)  
**شاخه مبنای بررسی:** main در commit 9da1253fdd04b1d1a6689347307e5157a3c61ab1  
**نوع بررسی:** بازبینی ایستا (Static Review) کد، مسیرها، سرویس‌ها، Viewها، CSS/JS، تست‌ها و Workflowهای GitHub Actions.  
**محدودیت مهم:** این بررسی به نشست واقعی کاربران در مرورگر Production یا داده زنده متصل نبوده؛ بنابراین وضعیت ظاهری در اندازه‌های مختلف، رفتار واقعی با موس/کیبورد و تأخیرهای محیط Production باید در مرحله‌ی E2E/مرورگر تأیید شود.

## جمع‌بندی مدیریتی

شیخان پایه‌های جدی یک سامانه‌ی واقعی آموزشی را دارد: کنترل دسترسی برای دوره و فایل، جداسازی اطلاعات نقش‌ها، تراکنش‌های خرید، مدیریت تلاش آزمون، محدودسازی نرخ در تعدادی از عملیات حساس و تست‌های گردش‌کار وجود دارند. اما کیفیت نهایی هنوز با «فقط سبز شدن تست‌های بک‌اند» تضمین نمی‌شود.

بزرگ‌ترین بدهی‌های قابل مشاهده:

1. **مرز دسترسی دانش‌آموز باید نقش عضویت در همان آموزشگاه را هم بررسی کند.** در نسخه‌ی مبنا، وجود عضویت فعال کافی بود، حتی اگر pivot آموزشگاه دیگر role=student نداشت. در شاخه‌ی ممیزی، شرط نقش اصلاح و یک تست رگرسیون اضافه شده است.
2. **CSS انباشته و overrideمحور شده است.** چندین فایل بزرگ selectorهای تکراری دارند. این شمارش به‌تنهایی باگ نیست، اما تغییر استایل را شکننده می‌کند و احتمال اثر ناخواسته روی صفحات دیگر را بالا می‌برد.
3. **تجربه‌ی نقش‌ها از یک سیستم بصری و تعاملی واحد پیروی نمی‌کند.** صفحه‌های دانش‌آموز یک shell اختصاصی با کلاس‌های قدیمی‌تر دارند؛ سایر نقش‌ها از layout مشترک‌تری استفاده می‌کنند. الگوهای فرم، کارت، پیام خالی، وضعیت عملیات و خطاها یکدست نیستند.
4. **ساخت CI در snapshot مبنا با Production قابل تفاوت بود.** Workflow تست ابتدا npm audit fix --package-lock-only را اجرا می‌کرد و lockfile را در زمان تست تغییر می‌داد. این تغییر در شاخه‌ی ممیزی حذف شده و تست JS/build اکنون با lockfile ثبت‌شده اجرا می‌شود تا با npm ci در Deployment هم‌راستا باشد.
5. **چند Service و View بسیار حجیم‌اند.** منطق مهم زیاد در آن‌ها جمع شده و بخشی از قوانین دسترسی/پیشرفت در چند query بزرگ بازنویسی شده است. این موضوع در تغییرات آینده احتمال drift و خطای بازگشتی را افزایش می‌دهد.

**توصیه:** پاکسازی را مرحله‌ای و با تست انجام دهیم. از rewrite بزرگ و هم‌زمان برای تمام نقش‌ها پرهیز شود؛ تغییرات دسترسی و انتشار اول، بعد یکپارچگی UI، و سپس refactorها.

## نقاط قوت تأییدشده در کد

- StudentAccessService برای دوره، درس، آزمون، تکلیف و پیوستن به کلاس بررسی‌های صریح دارد؛ محتوای پولی به وضعیت پرداخت و تراکنش تکمیل‌شده وابسته است.
- MediaController و MediaPolicy فایل‌های مرتبط با درس/آزمون/منابع/ضبط کلاس را از مسیر عمومی ساده جدا می‌کنند. رسید پرداخت نیز به‌صورت private ذخیره می‌شود.
- شروع و ارسال آزمون با transaction/row lock و کنترل مالکیت attempt انجام می‌شود؛ تلاش در حال انجام دوباره استفاده می‌شود و ارسال مجدد وضعیت نامعتبر را رد می‌کند.
- پیام‌رسانی دانش‌آموز و مدرس محدوده‌ی دانش‌آموز، مدرس، آموزشگاه و گروه کلاسی را کنترل می‌کند؛ تست‌هایی برای پاسخ‌دهی و حذف دسترسی بعد از لغو تخصیص کلاس وجود دارد.
- خدمات داشبورد Controllerهای کوتاهی دارند و منطق داده عمدتاً در Serviceهاست. برخی queryها eager loading، تجمیع، limit و pagination دارند.
- OwnerCacheService TTL کوتاه دارد و middleware پس از mutation موفق، cache داشبورد/گزارش مالک را پاک می‌کند.
- Deployment دستی و محدود به main است؛ Host key pinning، بررسی SHA، snapshot فایل‌ها، backup دیتابیس قبل از migration و cache/build در مراحل مشخص دیده می‌شود.
- تست‌های PHP برای نقش‌ها، خرید، محتوا، پیام‌ها، داشبورد و N+1 وجود دارند؛ Workflow تست SQLite و MariaDB را اجرا می‌کند.

## یافته‌های اولویت‌بندی‌شده

### P0 — قبل از اعلام آمادگی نهایی

#### 1. تفاوت lockfile تست و Production

**شواهد در snapshot مبنا:** .github/workflows/tests.yml در مرحله‌ی frontend، npm audit fix --package-lock-only را اجرا می‌کرد و بعد تست/build می‌گرفت؛ در مقابل، .github/workflows/deploy-production.yml با npm ci وابستگی‌های ثبت‌شده را نصب می‌کند.

**ریسک واقعی:** CI ممکن بود روی ترکیب وابستگی متفاوتی از Release آزمایش شود؛ بنابراین سبز بودن آن تضمین نمی‌کرد که assetهای Production با همان ورودی ساخته می‌شوند.

**اقدام انجام‌شده در شاخه‌ی ممیزی:** تغییر خودکار lockfile از CI حذف شده است. اکنون npm ci یک‌بار اجرا می‌شود، تست JS و build روی dependency graph ثبت‌شده انجام می‌شوند و artifact نیز lockfile ثبت‌شده را نگه می‌دارد. گزارش npm audit همچنان جداگانه و بدون دست‌کاری dependency graph ثبت می‌شود.

#### 2. کنترل نقش عضویت در سرویس دسترسی دانش‌آموز

**شواهد:** در نسخه‌ی مبنا، enrolledCourseIds() و academyMember() وضعیت active را می‌سنجیدند، اما نقش pivot آموزشگاه را به student محدود نمی‌کردند. در سامانه‌ای که نقش عمومی و نقش عضویت آموزشگاه جدا هستند، ممکن است عضویت از دانش‌آموز به نقش دیگر تغییر کند اما enrollment قدیمی باقی بماند.

**اقدام انجام‌شده در شاخه‌ی ممیزی:** شرط academy_user.role = student و wherePivot('role', 'student') اضافه شده و تستی اضافه شده که فعال بودن enrollment پس از تغییر نقش عضویت نباید دسترسی دوره یا درس را حفظ کند.

**وضعیت:** تغییر در شاخه‌ی audit/sheykhan-ux-prod-final-2026-10-24 است؛ تا پایان CI، آن را Fix تأییدشده‌ی Production تلقی نکنید.

**تعریف آمار:** شمارنده‌ی بالا یک بررسی متنی از تکرار رشته‌ی selector در بلوک‌های CSS است، نه AST کامل CSS. تکرار ممکن است برای breakpoint، حالت hover یا theme عمدی باشد؛ پس اعداد، میزان overrideهای قابل بررسی‌اند، نه تعداد قطعی باگ یا حذف قطعی کد.

**ریسک:** app.css هنوز selectorهای قدیمی teacher dashboard و exam editor را دارد، در حالی که teacher.css به teacher-dashboard.css هم import می‌کند. فایل‌های نقش نیز چند import مشترک دارند. باید با manifest و خروجی واقعی Vite بررسی شود که CSS مشترک چند بار در صفحه تحویل می‌شود.

**اقدام:** ابتدا style ownership هر component مشخص شود؛ سپس declarationهای تکراری درون همان component ادغام شوند. CSS آزمون/ویرایشگر، dashboard قدیمی و dashboard جدید باید از نظر دامنه‌ی selector جدا شوند. حذف کورکورانه‌ی آخرین override ممنوع؛ هر گروه باید با screenshot/DOM regression و responsive check تأیید شود.

#### 4. تجربه‌ی دانش‌آموز از سیستم بصری جدا افتاده است

**شواهد:** resources/views/layouts/student.blade.php از shell اختصاصی .app/.side/.main، SVG sprite و نوار جست‌وجوی مخصوص خود استفاده می‌کند، در حالی که layoutهای مالک/مدرس/والد از role-layout و کامپوننت‌های مشترک استفاده می‌کنند. student.css هم چند تعریف متوالی برای همان عناصر دارد.

**اثر برای کاربر:** رفع فاصله‌ی کارت، اندازه‌ی عنوان یا فرم در یک نقش لزوماً نقش دیگر را اصلاح نمی‌کند. تجربه‌ی responsive، پیام موفقیت/خطا و الگوی focus می‌تواند متفاوت بماند.

**اقدام:** به‌جای بازنویسی فوری کل Student panel، توکن‌های واحد رنگ، spacing، typography، اندازه‌ی کنترل‌ها، focus، alert و empty state استخراج شوند. سپس صفحات پرتکرار با اولویت Courses، Lessons، Assignments، Exams و Messages به این قرارداد مهاجرت کنند.

#### 5. مالک آموزشگاه: داشبورد بیش از حد شبیه فهرست لینک شده است

**شواهد:** resources/views/owner/dashboard.blade.php حدود 813 خط است و hero آن چندین اقدام سریع هم‌سطح (کلاس‌ها، اعضا، منابع، کتابخانه/محصول، showcase، سفارش، اسناد و گزارش‌ها) دارد.

**اثر برای کاربر:** صفحه بیشتر «کجا بروم؟» را فهرست می‌کند تا «امروز چه چیزی نیاز به اقدام دارد؟». وقتی همه‌ی گزینه‌ها در یک وزن بصری هستند، کارهای مهم مانند کلاس بدون مدرس، ثبت‌نام نیمه‌کاره یا ارزیابی منتظر ممکن است در میان لینک‌ها گم شوند.

**پیشنهاد UX:** بالای صفحه فقط 2–3 اقدام اصلی؛ سپس کارت «نیازمند پیگیری» با تعداد، دلیل و CTA روشن؛ بعد وضعیت عملیاتی و ابزارهای کم‌تکرار در بخش‌های گروه‌بندی‌شده. این تغییر باید بر اساس داده‌ی واقعی و مجوز هر نقش باشد، نه کارت ثابت یا mock data.

#### 6. پیام‌ها در چند صفحه و جریان جدا تقسیم شده‌اند

**شواهد:** صفحه‌ی دانش‌آموز در resources/views/student/messages/index.blade.php اطلاعیه‌ی آموزشگاه، پیام مستقیم مدرس، پیام‌های دانش‌آموز و پاسخ را در یک صفحه با چند paginator نشان می‌دهد؛ صفحه‌ی والد در resources/views/parent/messages/index.blade.php نیز ارتباط با آموزشگاه و مدرس را با چند فهرست و فرم جمع می‌کند. پیام‌های مدرس به والد و مدرس به دانش‌آموز هم مسیرهای جدا دارند.

**اثر برای کاربر:** ممکن است کاربر نداند باید پیام را از کدام بخش بفرستد یا پاسخ را کجا ببیند؛ چند پارامتر pagination هم‌زمان query string را شلوغ و حفظ context را سخت می‌کند.

**پیشنهاد UX:** ورودی اصلی «پیام‌ها» با تب/فیلترهای روشن مانند «آموزشگاه»، «مدرس‌ها»، «ارسالی‌های من»؛ badge وضعیت و زمان آخرین پاسخ؛ فرم فقط در جریان مربوط. هر لیست باید pagination مستقل داشته باشد و تغییر صفحه‌ی یک تب، context تب‌های دیگر را خراب نکند. قوانین دسترسی فعلی حفظ شوند.

### P2 — کیفیت استفاده و نگهداری

#### 9. اعتبارسنجی و بازخورد پس از اقدام یکسان نیست

در برخی صفحات، اعتبارسنجی نزدیک به فیلد، role=alert/status و پیام فارسی وجود دارد؛ در بخش‌های قدیمی‌تر، style inline و الگوی کلاس متفاوت است. معیار یکسان باید چنین باشد:

- هر خطا کنار فیلد مربوط و در summary قابل دسترسی باشد؛ داده‌ی معتبر واردشده پس از redirect از بین نرود.
- پس از Submit، دکمه حالت در حال ارسال/غیرفعال داشته باشد و double-click عملیات تکراری نسازد.
- موفقیت، خطای مجوز (403)، نبود منبع (404)، تعارض وضعیت (409/422) و خطای سرور پیام قابل فهم و اقدام بعدی مشخص داشته باشند.
- فرم حذف/تغییر وضعیت، تأیید واضح و بازگشت امن به همان فیلتر/صفحه را حفظ کند.

#### 10. تست‌ها بیشتر قرارداد سرورند تا سناریوی کامل کاربر

تست‌های Feature مفیدی برای دسترسی نقش‌ها، پیام‌رسانی، پرداخت، محتوای دوره و بعضی مسیرهای N+1 وجود دارد. اما تست‌های JavaScript اعلام‌شده در package.json فعلاً روی تقویم فارسی و ورود مبلغ متمرکزند. این مجموعه ثابت نمی‌کند که دکمه‌های داشبورد، theme، pagination، mobile nav و stateهای خطا در مرورگر واقعاً درست کار می‌کنند.

**اقدام:** پس از تثبیت CSS، حداقل سناریوهای مرورگر برای چهار نقش اضافه شود: ورود و redirect، ناوبری، ارسال فرم معتبر/نامعتبر، صفحه‌بندی، حالت خالی، موبایل، پیام موفقیت و ممنوعیت دسترسی. Screenshot regression روی عرض‌های موبایل، لپ‌تاپ و desktop برای صفحات کلیدی مفید است.

#### 11. مسیر Deployment محافظه‌کارانه است، اما Recovery باید صریح باشد

Workflow استقرار در صورت خطا بعد از فعال شدن maintenance mode سایت را fail-closed نگه می‌دارد. این تصمیم از بالا آمدن نیمه‌کاره بهتر است، اما به runbook عملی نیاز دارد: بررسی log، بازگردانی release/DB در صورت سازگاری migration، بازیابی snapshot فایل، و بازگرداندن سرویس فقط بعد از smoke test. migration مخرب نباید فقط با restore فایل‌ها rollback فرض شود.

| دانش‌آموز | ادامه‌ی یادگیری، پیشرفت و CTA کلاس/تکلیف؛ محدودیت دسترسی به محتوای پولی | یکسان‌سازی shell/CSS، کم‌کردن overrideها و تست واقعی موبایل، آزمون و پیام‌ها |
| والد | داده‌ی پیشرفت و منابع بر مبنای فرزندان مرتبط؛ پیام و پیگیری | خلاصه‌سازی پیام‌های متعدد و کمک به تشخیص اینکه «از چه کسی و درباره‌ی کدام فرزند» باید پیگیری شود |

## برنامه‌ی پاکسازی پیشنهادی

1. **دسترسی و CI:** ادغام fix نقش عضویت و lockfile پس از موفقیت CI؛ سپس همسان‌سازی نسخه‌ی PHP/Node در تست‌ها و Production.
2. **قرارداد UI:** تعیین توکن‌ها و کامپوننت‌های پایه؛ فهرست‌برداری از تمام CSS entryها و importها؛ خروجی build و manifest را برای CSS تکراری بررسی کنید.
3. **صفحه‌های کلیدی:** اول Owner dashboard و Student/Parent messages؛ اصلاح اولویت‌بندی اطلاعات، pagination و feedback بدون تغییر مسیر API/route.
4. **پاکسازی CSS/JS:** حذف overrideها فقط پس از ثبت رفتار فعلی و تست visual regression؛ تقسیم JS بر اساس feature.
5. **Backend maintainability:** متمرکز کردن قوانین دسترسی/پیشرفت و تکمیل تست‌های role change، membership removal، cohort boundary و حالت‌های race/double submission.
6. **Final audit:** تست کامل SQLite و MariaDB، JS tests، Vite production build، تست‌های مرورگر و smoke test روی staging. Production فقط بعد از مشاهده‌ی نتیجه‌ی سبز و بررسی واقعی صفحات.

## نتیجه

پروژه قابلیت تبدیل شدن به محصول Production را دارد و بخش‌های backend آن چند کنترل و تست خوب دارند؛ اما هنوز نباید صرفاً به‌خاطر وجود داشبوردهای متعدد و تست‌های Feature، آن را نهایی اعلام کرد. بزرگ‌ترین ریسک‌های نگهداری در حال حاضر، واگرایی قواعد دسترسی/داده، تفاوت dependency graph تست با استقرار، و انباشت CSS/JS و تجربه‌های بصری موازی است.

این گزارش یک ممیزی استاتیک از snapshot مشخص‌شده است؛ تأیید نهایی به CI شاخه‌ی اصلاحی و آزمایش واقعی جریان‌ها در مرورگر نیاز دارد.
